## Meeting Notes
### The Shift to AI-Driven Software Development & The Agentic Lifecycle (AIDLC)
*   The software engineering industry is undergoing a massive disruption, with abstraction layers collapsing and tasks that once took days now being completed overnight. This new velocity requires developers to let go of absolute control, embrace a "messy" initial process with AI, and adopt "epistemic humility."
*   Traditional practices, like strict "don't repeat yourself" rules, may be discarded in favor of raw speed. Developers must learn to collaborate with non-deterministic AI agents by letting go of their egos.
*   The Agentic Software Development Lifecycle (AIDLC) is a blueprint for this new workflow, involving three steps:
    1.  **Define Intent:** Clearly state the problem to the AI, treating it like a junior developer.
    2.  **Let it Run:** Allow the AI to autonomously execute the task, even if it makes mistakes.
    3.  **Human Verification:** The developer curates, "vibe checks," and guides the refactoring of the AI's output.
*   This approach, called "vibe coding," shifts the developer's role to an orchestrator of human-AI teams, where their value lies in defining intent, creativity, and curation. This has enabled massive velocity, with one developer shipping 100 pull requests in a single day.

### AI Maturity Levels and Organizational Strategy
*   A four-level AI maturity model was discussed:
    *   **Level 1:** Basic code completion.
    *   **Level 2:** AI assistance with some rules and guidance.
    *   **Level 3:** AI-first workflow with human assistance.
    *   **Level 4:** Fully agentic flow with humans in the loop for final verification.

### Proposed Layered Architecture for the AI Harness
*   A new layered reference architecture was presented to structure the discussion. The eight proposed layers are:
    1.  Model (core)
    2.  Interface (e.g., LLM gateway)
    3.  Orchestration Loop
    4.  Tools (sub-agents, CLI)
    5.  Context Management (retrieval)
    6.  Abstraction Layer (rules, conventions)
    7.  Persistent Memory (state)
    8.  Observability
*   An "agent" is defined as the model plus the harness plus the configuration. The architecture distinguishes between what is provided "out of the box" and what can be extended by the team.
*   A small group will draft the initial reference architecture explainer, integrating existing documents and diagrams stored on GitHub.
### Agent Design: Sub-Agents vs. Skills
*   A key architectural debate is whether to use sub-agents or skills to manage context bloat. Anthropic's guidance suggests "use skills unless you need fresh context."
*   Sub-agents can isolate work and return only essential outputs, while skills can accumulate context. The decision will be made on a case-by-case basis, with an emphasis on skills, but retaining sub-agents where isolation is needed.
*   This balance is expected to shift as larger, more capable models become available.
### Governance, Security, and the "Keymaker" Agent
*   A primary concern is governance and security. A "Keymaker" agent was developed to embed a standard governance and security layer into any agent it creates.
*   The Keymaker enforces consistency through templates (e.g., YAML files for definitions), manages ownership and repo access via DevOps, and uses a pre-flight checklist to validate user permissions.
*   The plan is to standardize agent-mediated deployments to mirror CI/CD controls, where only approved pipelines and security agents (owned by platform teams) can push to production.
*   A proposal was made to cryptographically sign ("stamp") all agent artifacts to prevent tampering, with runtime verification and key management via tools like Azure Key Vault. Security relies on standard ADO policies and scripted pipelines with PAT tokens.
*   All agents have a user guide tied to their definition and a proposal lifecycle for managing changes, resembling features or user stories in DevOps pipelines.
### LLM Strategy, Cost Management, and Benchmarking
*   A major concern is managing token costs, with one small group reporting an average spend of ~$70 per person per day, driven by powerful models (like Opus) and large context loading.
*   The team will create guidelines for model selection, distinguishing between "thinking" models for complex tasks and "non-thinking" models for simpler jobs. Enforcement will be necessary for automated workflows to use the "best value cost capable LLM."
*   A key unknown is the cost impact of switching between LLM providers mid-task, as it may reset the token cache. This requires investigation.
*   To control costs, the team proposed daily user budgets with overflow routing to cheaper models, gatekeepers with virtual API keys, and observability to track usage. However, the focus should be on "cost vs. value" analysis, measuring outcomes against token spend.
*   The team will build or adapt benchmarking frameworks to objectively evaluate new models against company-specific tasks (e.g., predefined code fixes).
### Team Structure, Productivity, and Agile Practices
*   AI-assisted workflows are showing strong efficiency gains, with one project delivering an estimated ~5 person-months of work in about two weeks of spare time.
*   Productivity has increased with smaller team sizes. The emerging practice is to use "pods" of 2-4 people (3 being optimal) within a larger team to reduce coordination overhead.
*   Each pod should include or have access to a technical subject matter expert (SME) to handle domain-specific refinement, offloading the Product Owner.
*   While development cycles are accelerating, the team agreed to retain agile ceremonies like retrospectives and goal alignment within a sprint-like cadence (e.g., two weeks), but with lighter, continuous refinement.
*   Productivity will be measured using existing dashboards for code quality, security, and effort estimates (e.g., maintainability score > 3.5), expanded with cost/value metrics for AI usage.
